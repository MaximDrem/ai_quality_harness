# Спецификация lib-ai-quality-harness

## Purpose

Harness SHALL выполнять сценарии оценки работы агента, описанные YAML-кейсами, собирать входные, промежуточные и финальные артефакты, применять выбранные функциональные и LLM-проверки и формировать воспроизводимые результаты.

Система SHALL позволять добавлять новый сценарий отдельными файлами данных, метрик и при необходимости обработчиков без изменения основного pipeline. Спецификация описывает текущий общий контракт и не вводит требований к конкретным будущим скилам или прикладным алгоритмам их проверки.

## Requirements

### Requirement: Автоматическое обнаружение и выбор сценариев

Система SHALL обнаруживать сценарии по наличию YAML-кейсов в независимых каталогах и SHALL позволять выбрать сценарий при запуске без регистрации в основном коде.

#### Scenario: Добавлен новый сценарий

- **WHEN** разработчик добавляет каталог сценария с хотя бы одним YAML-кейсом
- **THEN** система включает сценарий в список доступных без изменения CLI и загрузчика
- **AND** сценарий можно выбрать отдельным параметром запуска

#### Scenario: Сценарий не выбран

- **WHEN** пользователь запускает существующий набор без явного выбора сценария
- **THEN** система использует сценарий создания презентаций по умолчанию

#### Scenario: Выбран несуществующий сценарий

- **WHEN** пользователь указывает отсутствующий сценарий
- **THEN** система завершает запуск с ошибкой
- **AND** сообщает доступные варианты выбора

### Requirement: Явный состав проверок кейса

Система SHALL формировать чек-лист только из групп метрик, перечисленных кейсом, и его индивидуальных проверок. Система SHALL NOT подключать все проверки автоматически по одному типу артефакта.

#### Scenario: Кейсы выбирают разные метрики

- **WHEN** два кейса с одинаковым типом артефакта перечисляют разные группы метрик
- **THEN** каждый кейс получает собственный чек-лист
- **AND** невыбранные группы не выполняются

#### Scenario: Ссылка на неизвестную метрику

- **WHEN** кейс ссылается на отсутствующую группу метрик
- **THEN** система сообщает об ошибке с именем кейса и группы
- **AND** не выполняет прогон с неполным чек-листом

#### Scenario: Совпадающие проверки

- **WHEN** одна и та же проверка попадает в чек-лист через несколько описаний
- **THEN** система включает её в итоговый чек-лист только один раз

### Requirement: Независимые функциональные обработчики

Система SHALL загружать функциональную проверку по явной ссылке из YAML без центрального реестра. Полный путь обработчика SHALL допускать одинаковые имена файлов в разных доменах.

#### Scenario: Добавлена собственная проверка

- **WHEN** разработчик добавляет Python-модуль проверки и указывает его путь в YAML
- **THEN** система загружает и выполняет этот модуль
- **AND** основной код и реестры не требуют изменений

#### Scenario: Одинаковые имена в разных доменах

- **WHEN** два домена содержат проверки с одинаковым basename
- **THEN** система различает их по полному пути из YAML

#### Scenario: Обработчик отсутствует

- **WHEN** YAML ссылается на отсутствующий модуль или модуль без вызываемого обработчика
- **THEN** система возвращает понятный результат о недоступности проверки
- **AND** указывает проблемную ссылку

### Requirement: Переиспользуемые процессоры артефактов

Система SHALL отделять чтение и рендер артефакта от логики проверок. Система SHALL использовать существующий процессор для уже поддерживаемого типа файла и SHALL позволять добавлять новый процессор отдельным модулем.

#### Scenario: Существующий тип используется новым сценарием

- **WHEN** новый сценарий использует уже поддерживаемый тип артефакта
- **THEN** он может ссылаться на существующий процессор без копирования его реализации

#### Scenario: Процессор выбран явно

- **WHEN** артефакт или проверка задаёт процессор в YAML
- **THEN** система использует указанный процессор с приоритетом над автоматическим выбором по расширению

#### Scenario: Процессор выбран по расширению

- **WHEN** процессор не задан явно
- **THEN** система выбирает процессор, объявивший поддержку расширения файла

#### Scenario: Новый формат

- **WHEN** разработчик добавляет процессор нового формата и ссылается на него из YAML
- **THEN** извлечение текста и рендер работают через новый процессор без правки основного pipeline

### Requirement: Форматонезависимые общие проверки

Общие текстовые проверки SHALL получать содержимое через процессор артефакта и SHALL NOT зависеть от библиотек конкретного формата. Специализированные проверки MAY напрямую использовать библиотеку своего формата внутри соответствующего домена.

#### Scenario: Одна проверка для разных форматов

- **WHEN** одна общая текстовая проверка применяется к текстовому и Office-артефактам
- **THEN** оба файла обрабатываются через соответствующие процессоры
- **AND** код проверки не изменяется

#### Scenario: Специализированная проверка формата

- **WHEN** проверка использует свойства конкретного формата
- **THEN** её форматозависимые зависимости остаются внутри домена этого формата
- **AND** универсальные helpers не приобретают таких зависимостей

### Requirement: Входные вложения

Система SHALL принимать вложения из YAML-кейса, разрешать относительные пути от каталога сценария и передавать их агенту только с исходным сообщением.

#### Scenario: Относительный путь вложения

- **WHEN** кейс задаёт вложение относительным путём
- **THEN** система преобразует его в абсолютный путь от каталога сценария
- **AND** сообщает об ошибке до запуска агента, если файл отсутствует

#### Scenario: Продолжение работы агента

- **WHEN** система отправляет сообщение о продолжении после исходного запроса
- **THEN** исходные вложения не передаются повторно

### Requirement: Роли и выбор артефактов

Система SHALL поддерживать роли `source`, `intermediate` и `final` и SHALL позволять проверке выбирать артефакты по роли или уникальному имени из YAML.

#### Scenario: Проверка промежуточного результата

- **WHEN** проверка ссылается на имя промежуточного артефакта
- **THEN** она получает соответствующие сохранённые файлы
- **AND** финальные файлы не добавляются без явного выбора

#### Scenario: Проверка исходного и финального результата

- **WHEN** проверка перечисляет исходное вложение и финальный артефакт
- **THEN** контекст проверки содержит оба файла с различимыми ролями

#### Scenario: Неуказанный селектор

- **WHEN** проверка не задаёт селектор артефактов
- **THEN** система передаёт ей финальные артефакты по умолчанию

### Requirement: Сохранение промежуточных версий

Система SHALL сохранять промежуточные файлы при событиях агента и при рекурсивном обнаружении в рабочем каталоге. Каждая изменившаяся версия SHALL сохраняться отдельно до возможной последующей перезаписи.

#### Scenario: Файл перезаписан

- **WHEN** промежуточный файл изменяется между событиями
- **THEN** система сохраняет обе версии
- **AND** связывает каждую версию с исходным путём и порядковым номером события

#### Scenario: Одинаковые имена в разных каталогах

- **WHEN** в одном событии обнаружены промежуточные файлы с одинаковым basename в разных каталогах
- **THEN** их snapshot’ы не перезаписывают друг друга

#### Scenario: Неизменное содержимое

- **WHEN** повторно обнаружен файл с тем же содержимым
- **THEN** система не создаёт дополнительный snapshot-дубликат

### Requirement: Обнаружение финальных артефактов

Система SHALL рекурсивно обнаруживать финальные файлы в рабочем каталоге, включая вложенные выходные каталоги, и SHALL сопоставлять их с YAML-описаниями по типу и пути или glob.

#### Scenario: Финал во вложенном каталоге

- **WHEN** агент создаёт финальный файл внутри отдельного выходного каталога
- **THEN** система находит его по соответствующему относительному описанию
- **AND** короткое финальное сообщение без специального машинного протокола не мешает обнаружению

#### Scenario: Несколько обязательных финалов

- **WHEN** кейс объявляет несколько обязательных финальных артефактов
- **THEN** система ожидает наличия каждого из них
- **AND** отсутствие любого обязательного артефакта фиксируется отдельным FAILED

#### Scenario: Неоднозначное описание

- **WHEN** один файл соответствует нескольким разным именам финальных артефактов
- **THEN** система отклоняет конфигурацию с ошибкой, перечисляющей конфликтующие имена

### Requirement: Валидация готового файла

Система SHALL позволять оценивать готовый файл без запуска агента и SHALL проверять его существование и соответствие финальному описанию кейса.

#### Scenario: Валидация без клиентских side effects

- **WHEN** пользователь запускает валидацию готового файла
- **THEN** система не запускает sidecar
- **AND** не обновляет cookies
- **AND** не определяет модель OpenCode для имени результата

#### Scenario: Несуществующий или неподходящий файл

- **WHEN** входной файл отсутствует или не соответствует ни одному финальному описанию
- **THEN** система завершает валидацию с понятной ошибкой
- **AND** не применяет к нему проверки другого типа

#### Scenario: Вложенный путь в описании

- **WHEN** финальное описание содержит вложенный относительный путь
- **THEN** система сопоставляет его с соответствующей конечной частью пути входного файла

### Requirement: Параметры клиента и справочные режимы

CLI SHALL принимать режим авторизации и каталог конфигурации скилов с теми же значениями, которые поддерживает клиент. Справочные режимы SHALL NOT выполнять сетевые действия.

#### Scenario: Явные параметры клиента

- **WHEN** пользователь задаёт режим авторизации и каталог конфигурации
- **THEN** эти значения передаются в клиентскую сессию без дополнительного преобразования имён

#### Scenario: Запрошена справка или список сценариев

- **WHEN** пользователь запрашивает справку или список сценариев
- **THEN** система не запускает агента
- **AND** не обновляет cookies

### Requirement: Именование каталогов результатов

При полном прогоне система SHALL включать фактически выбранную модель OpenCode в имя каталога с датой и временем. Система SHALL формировать безопасное имя каталога и SHALL сохранять раздельные результаты по номеру прогона и кейсу.

#### Scenario: Модель задана аргументом

- **WHEN** модель передана явно
- **THEN** её нормализованное имя включается в каталог результатов

#### Scenario: Модель получена из конфигурации

- **WHEN** модель не передана аргументом
- **THEN** система использует эффективную модель из конфигурации клиента

#### Scenario: Специальные символы модели

- **WHEN** идентификатор модели содержит provider или недопустимые символы
- **THEN** provider удаляется
- **AND** недопустимые символы заменяются на `_`

### Requirement: Отчёты и ошибки оценки

Система SHALL сохранять детализированный XLSX-отчёт и SHALL отделять ошибки выполнения judge от отрицательных вердиктов по артефакту.

#### Scenario: Детализация по проверкам

- **WHEN** прогон кейса завершён
- **THEN** отчёт содержит отдельные строки проверок, результаты, обоснования, режимы и метрики
- **AND** сохраняет номер прогона и сведения о выполнении кейса

#### Scenario: Ошибка judge

- **WHEN** judge завершает отдельную проверку ошибкой
- **THEN** проверка получает статус ошибки оценки
- **AND** не учитывается как подтверждённый отрицательный вердикт по артефакту

#### Scenario: Уточняющий вопрос агента

- **WHEN** агент задаёт уточняющий вопрос вместо создания результата
- **THEN** кейс помечается исключённым из оценки с указанием причины
- **AND** вопрос сохраняется в данных результата

## Known Limitations

- Вложения материализуются клиентом внутри `uploads/`, а рекурсивный сбор финалов пока не исключает этот каталог. Широкий glob может принять исходное вложение за финальный результат; конфигурация кейса обязана использовать специфичный путь выходного каталога до отдельного изменения фильтрации.
- Валидация принимает один файл. При нескольких обязательных финалах остальные файлы считаются отсутствующими; комплексная валидация нескольких готовых файлов требует отдельного изменения CLI.
- Рекурсивное обнаружение ограничено рабочим каталогом агента. Финальный файл SHALL находиться внутри него; внешний путь из финального сообщения не является надёжной заменой.
- Прикладные алгоритмы сравнения содержимого исходных и финальных файлов не входят в корневой контракт и задаются отдельными изменениями соответствующих проверок.
